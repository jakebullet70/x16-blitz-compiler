**ATTEMPTED 2026-09-06 AND REVERTED.** The tree is green at `3335ab5`; none of this is in the repo.
Recorded because the mechanism was *proved to work* and the numbers were *measured* — the next
attempt should start from here, not from scratch.

**The problem it solves.** `FreeMemory` is `.align 256` immediately after the compiler's last
resident byte (`source/application/source/main/zzfree.footer`), and the object buffer runs from
there to `ObjectCeiling = $9F00`. So every byte of compiler comes one for one off the largest
program it can build. At `FreeMemory = $5200` the buffer is **19,712** bytes while the run side
would take **23,808** (15,616 low + 8,192 in one bank) — the compiler, not the machine, is the
binding limit. See [[compiler-must-not-cap-program-size]]. **Banking a user program does NOT
help**: the object buffer holds the low p-code *and* the regions, so the compile-side wall caps the
total either way.

**What is cold.** Bytes attributed to source modules by cross-referencing `build/code.lst` label
addresses with the files that define them: `gpasmcode.asm` 2,341, `gpbank.asm` 2,054,
`object.asm` 1,315, `gendata.asm` 1,271, `gpasmtable.asm` 626. The GP.ASM assembler plus its opcode
table is **2,967 bytes that a program with no `GP.ASM` never executes**.

**The mechanism, and it works.** A 64tass section declared late collects `.section` blocks from
anywhere earlier in the link:

    AsmOverlayImage:                ; PHYSICAL
            .logical $A480
            .dsection overlay
            .here
    AsmOverlayImageEnd:

placed after `FreeMemory` in `zzfree.footer`. The content assembles for `$A480` (inside a RAM bank)
and is emitted physically at the bottom of the object buffer, so it ships inside `GPC.BIN` with **no
extra file** — copied into the bank at startup, and the buffer takes the space straight back. Same
self-extracting trick `GP.BANKED` does for user programs.

Measured, in the real build: `AsmMnemonicTable` moved `$2F2C -> $A480`, `FreeMemory` moved
`$5200 -> $4800`, object buffer **19,712 -> 22,272 (+2,560)**.

**Three traps, all hit:**

1. **`.dsection` at root after `.send code` resets the program counter to 0** — the labels came out
   as `$0000`/`$0ACC` and no bytes were emitted. Fix: `* = FreeMemory` immediately before it.
2. **Every link that takes `compiler.library` must declare the section** or 64tass says
   `not defined 'overlay'`: `source/compiler/testing/testend.asm`,
   `source/runtime/testing/testend.asm`,
   `source/unit-tests/compiler-runtime/testing/testend.asm`. And `source/runtime/Makefile` links
   that same `testend.asm` **without** `compiler.library`, so the block there must spell `$A480`
   literally rather than name `AsmOverlayBase`.
3. `gpasmtable.asm` is **generated by `source/compiler/scripts/genasm.py`** on every build — editing
   the `.asm` does nothing, patch the generator's `h.write(...".section code"...)`.

**Why bank 3 specifically.** `AsmFixKind/Target/Value/Labels/Locals` already live at `$A000-$A47F`
in `AsmStorageBank = 3`, so putting the code at `$A480` in the *same* bank makes all **twelve**
`.asm_access` blocks inside the assembler no-ops — the macro saves bank 3, selects bank 3, restores
bank 3. Not one had to change. The blob pool cannot stay there (it started at `$A480`), so it moves
to a bank of its own and gets *bigger*: 8,192 instead of the 7,040 left over above the tables.
Only **three** routines touch the pool — `AsmPoolWrite`, `AsmFlushPool`, `AsmPoolPoke` — and they
stay in low memory, because code fetched from the window cannot change the window. The external
interface is only **twelve names**, of which five are routines needing shims and seven are storage
variables that stay put.

**WHY IT WAS REVERTED — UNRESOLVED.** With everything in place the compiler raised
`PROGRAM TOO BIG @ 23` on a *fifty-line* program, and on programs containing no `GP.ASM` at all.
Adding the missing `jsr AsmOverlayInstall` at the head of `CompileCode` did not fix it. Not
isolated: there are three raise sites (`api.asm` object ceiling, `storage/create.asm` variables,
`storage/mark_line.asm` line table) and I never established which fired. **Next time, instrument
first** — print `objPtr`, `lineNumberTable` and the variable pointer at the failure — rather than
reasoning about which one it "must" be. That guessing is what burned the session.
See [[measure-before-changing-code]].
